## Findings considered and rejected

- Auto-triggering the Store update via `UpdateAppByPackageFamilyNameAsync`:
  rejected — the owner explicitly asked to open the Store window so the
  client performs the update action.
- Checking "latest version" against the project's own pyupdategit manifest
  (`manifest_url`) instead of the Store API: rejected for this gate —
  Store certification lag would open the Store window when no update is
  available yet, dead-locking blocked users. The gate trusts only the
  Store's own `GetIsAppUpdateAvailableAsync` answer.
- Loop-and-wait inside the process until the package version changes:
  rejected — hostile to consoles/Task Scheduler and racy during package
  replacement; exit(1) + relaunch is the standard MSIX pattern.
